# Review (methods / evaluation): "Pipes, Files, or Handles? Revisiting IPC for LLM Agent Pipelines"

Reviewer focus: experimental design, statistics, metric validity, prompt fairness, generality.
I read `main.tex`, `numbers.tex`, the four figures, and the code in `src/agentipc/` (`pipeline.py`,
`metrics.py`, `judge_all.py`, `judge.py`, `analyze.py`, `paper_numbers.py`, `figdata.py`, `run.py`,
`workspace.py`, `data.py`, `configs/*.yaml`). I also recomputed a few quantities from
`results_raw/t07_main/20261118-212337-5d6c70f` and the k=8/k=16 runs. Those numbers are marked [recomputed].
Section 5's TODO experiments (cache pressure, fan-out at k=3) are not judged.

## Summary

The paper compares five ways of passing results between three Qwen3-8B agents (Researcher, Writer,
Reviewer) on bundled HotpotQA/2Wiki questions: full-history copy (A1), the same copy reordered so the
prefix cache reuses it (A1-zc), a pipe that forwards only the previous output (A2), a shared workspace (B),
a workspace with an auto-maintained index (C), and short handoffs that point into files (D). It counts cost
as tokens sent and as prefill tokens left after prefix-cache hits, and it uses an LLM judge to follow
supporting facts through the stages. Headline claims: copying is the most accurate channel. A1-zc keeps
that accuracy at 38–49% of the compute. Files send 1.8–4.8x the tokens and lose information when notes are
written (notes 27% shorter) and when they are read (unindexed readers skip them). An index recovers most
of the reading loss. All of these results depend on the KV cache size and on model scale.

The question is good. The testbed is clean: one variable changes, tasks are paired, run order is
shuffled, every macro is generated by a script, and each run has its own cache salt. The cost accounting
(sent vs. computed) is the most useful contribution. My concerns are about whether the file channels are
a fair implementation of file-based IPC, and how much the stage-level measures can be trusted. The
harness intervenes heavily in B/C. B's design withholds a naming convention that the harness does give
for its own files. Failure attribution (Fig. 3b) uses the lexical matcher, not the judge the text
describes. The judge was never checked against human labels. Each (task, channel) pair runs once even
though identical prompts give different outputs 41% of the time, and no multiple-comparison control is
applied. Several sentences say more than the code or data support (list at the end).

**Score: 3 / 5** (weak accept for a workshop. The core cost finding is solid. The information-loss story
and the "files lose" conclusion need the fixes below before I would trust them.)
**Confidence: 4 / 5**

## Strengths

1. The design isolates the channel. Researcher inputs (user content) match across channels, tasks are
   paired, the job order is shuffled across channels and k (`run.py:78`), and each run has its own
   `cache_salt`, so no channel benefits from another channel's KV.
2. Counting cost two ways (sent vs. computed) is the right move and is new for agent communication. The
   2.9x-sent / 0.79x-computed contrast for files is a clear, useful result. The k=8/k=16 sweep shows when
   it stops holding.
3. Reproducibility is good. `paper_numbers.py` writes every number in the text, figures read only
   `results/`, and configs are checked in.
4. The sensitivity section asks the right questions (budget, batched reads, longer chain, smaller model,
   payload size). Several of its findings are interesting: the checker helps the pipe, and cheap bulk
   reads make the Writer skip the notes.
5. The accuracy ranking survives stricter metrics. [recomputed] Under exact match, k=3 pooled: A1 60.8,
   A1-zc 59.0, A2 50.2, B 53.7, C 56.1, D 53.6. Under F1 the order is the same. The lenient matcher is not
   what creates the main ordering.

## Weaknesses (most important first)

### W1. The file channels are partly handicapped by the harness design, so "files lose" may be a property of this harness rather than of files.
- **No naming convention for notes in B.** The harness fixes `draft.md`, `checked.md`, and `final.md`,
  and tells readers those names (`OUTPUT_FILES`). The Researcher alone is told to "choose the file names
  and how to split them". The B Writer then has to guess which of ~33 files holds the notes. The paper's
  own explanation of B's reading loss is exactly this ("The file list does not say which file holds the
  notes"). Any real system would give notes a known path, as the harness does for everything else. As it
  stands, B is a strawman for the reading-side result.
- **C differs from B in three ways, not one.** It adds (i) the index, (ii) an extra Researcher
  instruction, "Start each notes file with a heading that says which questions it covers"
  (`INDEX_RULE["researcher"]`), and (iii) an index that also lists every source document's first line,
  i.e. a title map. The text credits everything to "the index".
- **Fixed 12-call budget for every k.** At k=3, 34% of B and C runs hit the limit [recomputed;
  `turn_limit` 0.343 for both]. At k=16, the B Writer hits it in 19/60 runs and the B Reviewer in 31/60
  [recomputed, `t08_large`]. The 24-call check was run only at k=3 on 50 tasks per dataset, and 14–16% of
  runs still exhausted even that budget. The "plain files collapse" result at k=16 (−34 points, Fig. 4b)
  is therefore confounded with a budget that does not scale with the work.
- **Fix:** add B′ = B with a fixed notes path (`notes.md`) that is told to the readers. Add C′ = B plus the
  heading instruction but no index, and possibly an index that lists agent files only. Make the budget
  scale with k (e.g. 4 + 2k), or rerun k=16 at 24/48 calls. Report how B′ and C′ compare to A1.

### W2. The forced final write is a large, unreported intervention.
- [recomputed, k=3] The forced `write_file` call fired for the Writer in 59% of B runs and 39% of C runs,
  and for the Reviewer in 34% (B), 46% (C), and 34% (D) of runs. In those runs a third to over half of
  the file-channel drafts and final answers come from a call where the harness forced the tool and said
  "Save your output to draft.md now", often right after the budget ran out. Message channels never get
  this help or this pressure. The paper describes the mechanism in one sentence but gives no frequency.
- **Fix:** report the forced-write rate per channel, role, and k. Report accuracy separately for runs
  with and without a forced write. Add a sensitivity run where a missing output file counts as failure
  (no rescue), so readers can see the direction of the bias.

### W3. The failure attribution in Fig. 3b uses the lexical matcher, and its category order is not "first stage".
- `figdata.fig3` plots `q_*` fields, computed in `metrics.failure_types` with `fact_present` (≥50% of
  anchor tokens). The judge-based version (`judge_all.judged_failures`, `jq_*`) exists in code but is
  absent from `judged.jsonl.gz` [recomputed: the keys are only `judge_*`]. Fig. 3a uses the judge and
  Fig. 3b uses the lexical matcher, and the two disagree a lot. Mean per-run notes recall is 0.46
  lexical vs. 0.69 judge, with a per-run correlation of 0.46 [recomputed]. Because `research_miss`
  requires *all* of a question's facts to pass the lexical test, "Researcher missed" takes 20–31% of
  questions even in A1, and "Not delivered" is almost empty (0–1.1%). Fig. 3b's main visual message
  ("most errors are research misses") may be an artifact of the matcher.
- `failure_types` checks `reviewer_broke` before `research_miss`, so a question is attributed to the
  Reviewer even when the Researcher missed facts. That contradicts "the first stage that explains it".
  It also ignores that in A1 and B–D the Writer and Reviewer can read the source documents, so a missing
  note does not by itself explain an error.
- **Fix:** regenerate Fig. 3b from `jq_*`, or say clearly that it uses lexical matching. Order the
  categories by pipeline stage, or call the scheme a priority order. Report how often wrong answers had
  all facts in the notes.

### W4. The LLM judge has not been validated, and its validation target is the wrong reference.
- The judge is Qwen3-8B, the same model that produced the text. It is also used for the 4B runs. The
  only agreement check (`judge.py`, kappa 0.72 in a smoke run) is (a) not reported in the paper, (b)
  measured against the lexical matcher, a weak proxy (see W3), not against humans, and (c) measured with a
  *different prompt* than the deployed judge: one fact per call, 12k-character truncation, and a one-word
  answer. `judge_all.py` instead batches all facts of a question and truncates at 60k characters.
- Self-judging could favor the model's own phrasing in message-channel notes over terse file notes. The
  27%-shorter-notes finding is exactly the kind of difference such a bias would inflate.
- **Fix:** hand-label about 200 (fact, text) pairs stratified by channel and stage, and report judge-vs-
  human kappa per channel. Add a second judge from a different family on the same sample. Validate the
  prompt that was actually used.

### W5. The delivery metric is asymmetric across channels.
- For message channels `writer_input` is the Researcher's reply only (`pipeline.py:372–373`), so
  delivery is ~100% by construction. The reported 99% just measures how consistent the judge is with
  itself on the same text. In A1 the Writer also receives all documents, but they are not counted. For
  B/C/D, `writer_input` is everything the Writer *read*, including source documents (83% of B's reads).
  "Facts in the notes that reached the Writer" therefore means "via the notes" for A1/A2 and "via
  anything" for B–D.
- **Fix:** define delivery the same way everywhere: facts in the notes that also appear in note-file
  reads (or the copied notes). Report the doc-read route separately. Say in the text that message
  channels get 100% by construction.

### W6. Run-to-run nondeterminism is large and the design does not quantify it.
- Identical Researcher prompts give different notes in 41% of tasks. Each (task, channel) runs once, so
  the paired bootstrap captures task-to-task variance but not run-to-run variance within a task. The
  sensitivity comparisons pair a *new run in a different session* against the main run (chain4, Bb,
  24-call, `paired_with_main`), so session drift and batch composition are mixed into each delta.
- **Fix:** add an A/A control. Rerun A1 and B on 100 tasks in a separate session and report the paired
  accuracy difference and its CI. That is the noise floor for every cross-session delta in Section 5. If
  budget allows, use 3 repeats per (task, channel) on a subset and a hierarchical bootstrap (tasks, then
  repeats).

### W7. Multiple comparisons, and equivalence claimed from non-significance.
- The main grid alone has 5 channels × 6 cells = 30 CIs, the 4B grid 20 more, and Section 5 more again.
  "Significant in 5 of six settings" is uncorrected. "Within the noise of it in every dataset and k"
  infers equivalence from failure to reject. [recomputed] Under EM, A1-zc is significantly below A1 on
  2Wiki at k=3 (−3.6 [−7, −1]) and k=5 (−3.2 [−6, −1]). Under the lenient metric, 2Wiki k=3 is −2.7
  [−6, +0]. So the equivalence claim depends on the metric.
- **Fix:** use Holm–Bonferroni within each family, or fit one mixed-effects logistic model (question-level
  correctness ~ channel × dataset × k, random effect for task). For A1-zc ≈ A1, run a TOST with a
  pre-stated margin (e.g. ±3 points) and report EM alongside the lenient metric.

### W8. "Writing to a file changes the writer" is confounded.
- The file-channel Researcher gets a different system prompt: "other agents cannot see your reply... in
  one or a few calls". It must emit its notes as a JSON string argument, and it is told to split files.
  [recomputed, k=3] Its calls hit `finish_reason=length` (2048 tokens) in 7.3% of B runs and 3.3% of C
  runs, vs. 0.3% for A1/A2. Notes are empty in 5.0% of B runs and 3.3% of C runs. `written_by` reads the
  current file contents, so a non-append rewrite silently drops earlier notes. A useful comparison point:
  A1-zc's Researcher, which only moves the instruction to the end, writes 1,992 characters vs. A1's 1,570
  (+27%). Note length is about as sensitive to prompt form as to the channel.
- **Fix:** remove the length truncation (raise `max_tokens` for write calls), exclude or report empty and
  truncated notes, and add a control where the message-channel Researcher gets the same "save your notes"
  instruction but replies in text. Report the 27% with a CI and with A1-zc included.

### W9. Cost and latency accounting is incomplete.
- "Tokens sent" adds input and output tokens. APIs price output higher and discount cached input, and the
  paper's own A1-zc argument depends on that discount. "Tokens computed" counts prefill only and ignores
  decode tokens and per-call overhead, both of which grow with file-channel call counts (17 calls vs. 3).
  The contribution list says the testbed accounts for latency, but no wall-clock number appears in the
  text, even though `nWall*` macros exist (B is 1.8x A1).
- **Fix:** add a priced-cost column using a public price sheet (input / cached input / output). Report
  decode tokens. Report wall time with its CI, and say it was measured at concurrency 6 per server.

### W10. Generality.
- One model family (Qwen3-8B, plus 4B) with thinking disabled and the Hermes tool parser. One task type
  (multi-hop QA with ~30 paragraphs, all of which fit in one prompt). Linear chains only. This is the
  regime where copying should win, and the paper admits as much. For a workshop on agents, at least one
  stronger tool-using model (a larger open model or an API model) and one task whose artifact is larger
  than the context (or a long-report task) would show whether the "share files only with an index and a
  capable model" rule generalizes.
- Smaller points that also limit generality: the k=16 setting changes two things at once (k and three
  parallel Researchers), and sample sizes outside the main grid are small and not stated in the text
  (k=16: 60 tasks total; k=8: 200; the pending cache-pressure config uses `use_tasks: 5`, i.e. 10 tasks
  per condition).
- **Fix:** state n in every sensitivity paragraph and in Fig. 4's caption, add CIs to Fig. 4, and once the
  fan-out run finishes, use it to separate k from fan-out.

### W11. Minor fairness and leak issues.
- File names give file channels structure that message channels lack. Doc IDs are assigned in question
  order *before* the shuffle (`data.py`, `d{len(docs):03d}` and then `rng.shuffle`), so `list_files`
  (sorted) groups each question's ten paragraphs together, and the names carry title slugs. Message
  channels see the shuffled order.
- A2 is the only channel whose downstream agents cannot see the source documents. Its Reviewer failure
  is partly a result of withholding access, not only of the channel shape. That is fine for a pipe, but
  the text should say it.
- Fig. 2's error bars are unpaired pooled CIs, while the text argues from paired differences. Say so in
  the caption.

## Questions for the authors

1. What is B's accuracy if the Researcher must write `notes.md` and readers are told that path? Does the
   B-vs-C gap survive?
2. What is the accuracy of B/C/D runs that needed a forced write, compared with runs that did not?
3. How does the judge agree with human labels, per channel and stage, using the deployed batched prompt?
4. Why does Fig. 3b use lexical attribution while Fig. 3a uses the judge? What does Fig. 3b look like
   with `jq_*`?
5. What is the A/A noise floor (same channel, two sessions) for accuracy and tokens computed?
6. With a k-scaled tool budget, does B still lose 34 points at k=16?
7. Where are the CIs behind "both changes exclude zero at 95% on 200 paired tasks" (chain4) computed?
   `paper_numbers.chain4` computes only means.
8. Were the cache-hit rates for A1-zc at k=8 checked against server-side eviction counters? Or is "no
   longer fit the KV cache" inferred only from the prefill ratio?
9. Is the 4B result partly caused by the judge? 8B judges 4B text, and the 4B Researcher may paraphrase
   differently.

## Sentences that overclaim or do not match the code

1. Abstract / §4: "agents write 27% shorter notes to files" and "the same Researcher, given the same input,
   writes 27% shorter notes when they go to files". The system prompt differs (`OUTPUT_FILES` vs.
   `OUTPUT_MSG`), 7.3% of B Researcher runs are truncated at `max_tokens`, and 5% of B notes are empty.
   The inputs are not the same, and the size of the effect is confounded (W8).
2. §2: "The Researcher's input is identical in every channel: the questions and all documents." Only the
   user message is the same. The system prompt differs per channel, and in A1-zc the instruction moves to
   the end (`build_messages`, lines 270–275), which changes note length by +27%.
3. §4: "Zero-copy broadcast is within the noise of it in every dataset and k." This is non-significance,
   not equivalence, and under EM 2Wiki k=3/5 is significantly lower (W7).
4. §7: "zero-copy broadcast was the most accurate channel". A1 (72.3) is the most accurate. A1-zc (71.6)
   is statistically indistinguishable from it, at best.
5. §4: "their Writer and Reviewer make 17.0 and 15.9 calls instead of one". `nCallsB` is `llm_calls`
   summed over *all* agents, Researcher included (A1 = 3.0). It should read "the pipeline makes 17.0 and
   15.9 calls instead of 3".
6. §5: "on 100 paired tasks per dataset and channel" (24-call budget). `t08_turns24` uses `use_tasks: 50`,
   and `nTwFourN` = 100 is pooled over both datasets. It should be 50 per dataset.
7. §5: "both changes exclude zero at 95% on 200 paired tasks". No CI is computed for chain4 in
   `paper_numbers.py`. The comparison is also cross-session (W6).
8. §3 Metrics: "Fact delivery uses Qwen3-8B as a judge ... For each wrong answer we record the first stage
   that explains it". Fig. 3b uses lexical matching (`q_*`), and the code ranks `reviewer_broke` before
   `research_miss`. Neither is first-stage attribution by the judge. The paper also omits the `no_answer`
   and `overflow` categories.
9. §4: "Its losses are not in delivery: the Writer receives everything the Researcher wrote." True by
   construction (`writer_input` = the copied notes). The 99% figure is judge self-consistency, not a
   finding.
10. §4: "only 74–86% of the facts in B's notes reach its Writer". `writer_input` for B includes source
    documents the Writer read, so this counts any route, not reaching the notes. The number for A1 is
    defined differently (W5).
11. §1 contributions: "accounts for tokens sent, tokens computed, latency, file I/O". Latency is never
    reported.
12. §5: "The tool budget does not drive the results." Shown only at k=3. At k=16, 32% of B Writer runs
    and 52% of B Reviewer runs hit the 12-call limit, and that is the setting behind "plain files
    collapse".
13. Abstract / §5: "at large payloads plain files lose 34 points". This is n = 60 tasks with a fixed
    budget and three parallel Researchers. The finding should be qualified (W1, W10).
14. §5: "Differences of a few points need the paired tasks we use." Pairing removes task variance, not
    run-level nondeterminism. That needs repeats or an A/A control.
15. §5 (4B): "The index no longer helps." Pooled 4B accuracy is C 41.4 vs. B 37.1, and no paired C−B test
    is reported. "Helps less" is what the data show.
16. §5 (4B): "it reads its instruction last, after thousands of tokens of documents." This is a causal
    explanation that was not tested. Present it as a hypothesis, or test it, e.g. by repeating the
    instruction at the top.
17. §5: "six concurrent runs no longer fit the server's KV cache together". Inferred, not measured. No
    eviction or hit-rate counters are reported (pending experiment).
18. §7: "plain files cost more tokens and lost accuracy everywhere". This holds in this harness. Given W1
    (no notes path, fixed budget, forced writes), the claim should be limited to this B design.
